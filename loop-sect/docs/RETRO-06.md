## 做得好的

1. **純函式＋共用一步。** M15 的 `runTrial` 跟遊戲用同一個 `trialTick`，所以「遊戲裡的成績等於開始時的模擬」可以直接測，soak 量主張也不必改世界，舊雜湊一個都沒動。
2. **第二組種子照規則用了。** M15、M16 的主張都在兩組種子上量；M16 的「舊指標退步」也兩組都量，才看出種子 13–24 的 exp 本來就不過。
3. **先診斷、找不到原因就停。** M16 第二次後用三個不留的變體（拿掉走慢、讓傷者迎敵、關掉受傷）排除了兩個猜測；找不到單一原因就沒有做第三次碰運氣，直接退回、問擁有人。
4. **舊雜湊與 report 逐行比對**仍然是最便宜的保險：兩次暫停都能保證預設行為一點沒變。

## 做得不好的

1. **同一類粗估錯第四次。** v6 已經寫「選擇比例的粗估寫出選法並先量」，M16 還是假設藥畦「沿用菜園」就會有人種——其實播種在候選裡排第 13–23；煎藥也從沒排第一。規則寫在清單上，但沒有一個工具讓我在量之前順手看。
2. **用中位數估長尾。** 受傷是迎敵被扣的精力累積起來的，我用每段的中位數 3.6 估「受傷約占 5%」，實際是 14%：傷是長尾那幾段造成的，持續時間也是。
3. **暫停越積越多。** 五個暫停裡三個卡在 M10-A5 的 2%。這輪量到：只放一座藥園（不受傷）herb 情境的最差日就到 3.0%／3.7%；種子 13–24 的 exp 不動任何東西也是 3.3%。這條門檻離雜訊太近，任何會改到日常節奏的新東西都會碰到它。這不是單一 milestone 的問題，是舊門檻的問題。
4. **headless 在機器忙時不穩。** m15-trial 的像素檢查在 soak、report 並行時取到暫停前那一幀，0/2；單跑兩次都過。已改成取像素前等兩幀。
