## 做得好的

1. **soak 是這三輪最有價值的工具。** 兩個最嚴重的問題（又餓又累的死循環、人物大半時間在走路）單元測試都過了，只有多種子長跑看得出來。而且每輪的不變量會一直累積：loop 3 改移動速度時，M1 的不瞬移、M2 的存活與作息都在同一次 soak 裡被重新驗過。
2. **決定論讓除錯很便宜。** 同種子可以完全重播，所以診斷腳本能直接數「飢餓時每人在做什麼」，不用猜。
3. **規格先寫、驗收有編號**，所以每輪的「完成」都對得到具體檢查，紀錄裡寫得出哪條靠哪個測試過。
4. **證據不進 git。** 截圖寫到 gitignore 的 `.evidence/`，三輪下來 repo 只多了程式和文字。避開了 GPT 分支證據 1.69GB 的問題。

## 做得不好的

1. **驗收條件寫的時候沒有先估可不可行。** M1-A7（外向者整體離人比較近）在有了吃睡之後被聚集效應蓋掉；M3-A4（茅屋蓋好一定有人睡）在三人三床時本來就不會發生。兩條都是中途才改成控制實驗。改得有道理，也都記錄了，但這代表規格那一步少了一道檢查。
2. **先調數字、後診斷。** loop 3 第一次 soak 失敗後，我先試了三組數字（吃飯權重、缺糧分母、活計基礎），飢餓時間反而從 4.6% 升到 18%。直到印出「每人每 tick 在做什麼」的分布，才看到真正的原因是走路占大宗。如果一開始就看分布，可以省掉兩輪試錯。
3. **回頭改前面 milestone 的數字，規格要跟著手改。** 移動速度與飯量寫在 M01、M02 規格和 `data.mjs` 兩個地方，改的時候要記得同步加註，容易漏。
4. **畫面沒有 gate。** headless 只檢查 DOM 與狀態，畫面好不好看只靠我每輪看一兩張截圖。例如 loop 2 才發現橋沒畫出來，是看圖看到的，不是檢查抓到的。
5. **只有作者自己審。** 自我審查清單每條都勾了，但三輪都沒有第二雙眼睛或真人試玩，平衡也只用 soak 的數字判斷「好不好玩」。
6. **診斷腳本放在暫存目錄，沒有留下來。** 下次遇到同類問題要重寫。

## 對下一輪的風險

- 走路仍占 48.8%。M4 技能如果讓「做事變快」，走路占比會更高，玩家會覺得成長沒感覺。M4 規格要把「成長要讓整趟變快，不只是做事那一段」列進驗收，或同時考慮腳力／搬運量。
- 三個人、三張床、單一倉堆的規模下，很多規則還沒受到壓力（預約搶奪、多工地排序）。M5 人際和 M8 招人之後人數會變多，現在的效用 AI 每次會掃全地圖的樹，需要在人數上升前量一次效能。
