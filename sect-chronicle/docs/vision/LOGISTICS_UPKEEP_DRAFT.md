# 實體資源、物流倉儲與人口維持：長期草案

狀態：**擁有人草稿收錄／待討論／實作未排程**。日期：2026-10-20；整理：Codex（Earth PO）。[聊天原稿](sources/2026-10-20-logistics-upkeep-original.md)／[願景入口](README.md)／[Proposal #160](https://github.com/lalagrass/earth-ascension/issues/160)。使用者要求「這份草稿也幫忙整理收錄進來」，授權保存、評估及 backlog 整理，未批准新生存規則、數值、正式 Godot 遷移或程式實作。

## 想保留的體驗

採集、搬運、儲存與使用能在場景中看見；每多一位成員，同時多了勞動／學習的可能與照顧責任。安排後勤、改善設施或學會術法，能釋放原先反覆勞作的時間，回到修行、授課、交往與探索。從破廟到有人生活的道觀，成長既是角色的，也是聚落的。

這是值得驗證的經營假說，尚非「完美閉環」或已證實好玩。原稿《RimWorld》《工人物語》《天誅/太吾》只保存為作者體驗參照，本輪未核實其共同核心或內部實作。資源耗盡、工作變忙或產量變高，也不能直接證明心流；需確認玩家是否看懂、有選擇且願意繼續玩。

## 原意與 PO 建議

| 草稿方向 | 保留的價值 | PO 建議與代價 |
|---|---|---|
| 水／木料／糧肉／電力 | 挑水、砍柴、炊事、藥圃與設備有可見用途 | 先驗一種資源與一條使用鏈，不同批加入三餐、取暖、灌溉、冰箱和電網。電力是供需／設備能力候選，不先當成與水同義的可堆疊貨物 |
| 按人口用水、飲食、床位 | 收徒有準備與照顧責任，住房能改變生活 | 人也有技能、陪伴與貢獻；比較增員前後淨負擔，不把招募設計成純懲罰。床位先比較容量表達與真實睡眠流程，不直接新增完整作息 |
| 水缸水位、柴棚、實體搬運 | 看得出去哪裡、帶什麼、存在哪裡、為何等待 | 比較「倉儲節點＋在途載貨」與逐件落地堆疊；前者可先驗空間取捨，後者需放置、拾取、阻擋與大量物件成本，不預定全面逐格實體化 |

| 藍圖→搬料→施工 | 建造有準備、進度與完工回饋 | 現有 RT 已有移動與非瞬間建造；新增的是實體材料運送與分階段語義，不能把現有功能當不存在而重造建造系統 |
| 手作→土木設備→道法自動化 | 改善路線／工具／設施可釋放時間；世俗工藝與修行互補 | 先比一個改善前後的時間分配；現代採購／汽油／電力、雨水與術法各需世界觀／來源／代價，非既定科技樹或每局必走進度 |
| 缺貨下限自動派工 | 減少手點，玩家訂方向、角色處理細節 | 沿既有需求計算／預約／正式指令，先做可解釋補貨；不按資質高低永久鎖後勤，不強制每日同時派兩人，保留輪替／分工與介入 |

## 數值與例子的待釐清處

原稿所有材料、尺寸、耗量、容量、百分比、天數、倍率與電力值均為**未校準示意**，不移入 rules、驗收門檻或效能承諾。原稿完整保留，不為消除矛盾暗改作者數字。

- 每人每日水 2 單位，但範例每小時扣 0.15，若一天 24 小時即 3.6；需先定世界時間尺度、單位、扣除頻率與取整。現有 RT tick 不直接等於此例的小時。
- 水缸文字列 50／100／200，設施表是 60，程式是 100；需區分型號／升級或選一個有限情境。兩桶各5是每趟10，不等於任一缸的日需。
- 「兩人每週挑一次」與「八名弟子天天見底」不是可推出的結論：需列是否含師父／主角、每趟運量／趟數、缸初值／容量、炊事灌溉等需求。僅按每人2／日，兩人一週28，八人每日16；若另有師父／主角則不同，這些只是草稿條件的算術，不是建議平衡值。
- 肉食不足恢復降低40%、常溫3日腐敗、路速+25%、雨天蓄水翻倍、一人十倍運力，皆需用途、上限與取捨；不以「外家拳」或資質標籤直接決定唯一飲食／後勤路線。
- 抽水5單位／時與15W尚不足以構成遊戲供電模型：水的單位、可用電力、晝夜／天候、是否儲能／備援、停電處理與維修尚未定；本輪不作真實設備工程驗證。
- 缸乾造成心境暴跌、無床持續懲罰等先留候選。先定預警、寬限／應急補給、降低需求或暫緩招募等恢復路徑，避免缺水→沒力搬水→更缺水的不可逆循環。

## 與現行世界／程式的差異

依 [RT-00](../RT00_CONTRACT.md) 的單一權威 tick、旅行／工作、原子預約與 R2 需求生成，已有從目標找材料、扣成本、占工作位、移動與完工的流程。現行資源／庫存不是本稿的水、木、食物與電力；R2 也不是已完成的人口消耗或實體搬運。本輪只盤點可復用責任，不承諾無縫接線。

RT-00 §4.4 已批准的日常維持 A 是目標完成後依既有條件休養／突破／有原因等待；等待本身不改資源與體力，補貨至新上限的替代 B 尚未批准。本稿 Upkeep／自動補貨是未來新規則，不能因名稱也叫「維持」就覆寫 A 或啟用 B。

原稿 Godot `ResourceManager`／`JobQueue` 是概念範例，未接可回放世界，也未呈現各倉位置／在途貨物。沒有證據表明全域 Singleton 是本專案必須架構；`broadcast_to_disciples`／工作列方法在稿中未定義，不能直接執行、宣稱有行為樹，或照譯出第二套 JS 管理器。#155 的 PixiJS／Godot 比較仍只授權其獨立 UI 試作。

未來若批准這些玩法，先以短契約決定以下問題，再做最小整合；現在不新增 schema／API／通用物流框架：

1. **帳目與歸屬**：庫內實存、已預約、在途、消耗與損失分清；資源不能離開來源又仍可花用，也不能入缸及完工各加一次。需求不能只看當前庫存而忽略預約／已派在途補給。容量也須預約，避免多人回程同時溢出。
2. **工作生命週期**：取貨→運送→交付與建造現有「出發扣料」如何相容？材料遺失／改目的地／取消／中斷施工的歸還位置與費用先定，不可既退款又留下可再用的貨。這是新契約選項，不擅改 D9 的取消語義。
3. **唯一時間**：Upkeep、腐敗、供水、施工都由正式世界時間推進。暫停不消耗，背景／離線是否前進沿既有控制器契約，不能靠 Godot timer／瀏覽器每幀／真實時鐘暗扣。讀檔不補扣或重發貨，倍率不改同 tick 結果。
4. **補貨與仲裁**：原稿每小時低於下限就貼工作，可能重複排單；按缺口與在途量去重，考慮回補上下限／重新決策時點。缺來源、倉滿、路不通、人忙／疲勞要有原因和重試條件，不能每幀搶單或強制蓋掉玩家指令。
5. **消耗與警示**：原稿只扣水，木料／食物／床位尚無實作；下限每小時廣播也會重複抱怨。先比較短缺狀態轉換通知／持續可見警示與原因，精確短缺量不能被 `max(...,0)` 抹去。個人喝水和全域 Upkeep 是否同筆消耗須唯一，不能重扣。
6. **建造與阻擋**：藍圖／施工／可使用各有狀態，未完工不可預約成品；多人搬料／施工、占地與通路、最終交付等須與既有仲裁一致。只做路線／倉節點表達時不承諾房間建造與連續尋路。

## 候選拆分與可見驗證出口

細項索引見 [FUTURE_BACKLOG 的 BL-G01～G05](../FUTURE_BACKLOG.md#資源物流與人口維持候選bl-g01g052026-10-20)。以下是可選的學習順序，非實作指派或硬性全串依賴；依 [D12 交付規劃](../VISIBLE_DELIVERY_PLAN.md)選下一個最小問題，可能只留紙上結論。

| 候選 | 一個玩家問題／最小情境 | 保留／調整／延後的依據 |
|---|---|---|
| G01 存量與用途 | 一種資源、一個倉與使用點；短流程看進出、餘量、誰將用它 | 能否說出「為何需要搬／何時夠用」；先比較節點庫存與逐件堆疊，沒有新模型就只交圖／流向表 |
| G02 空間搬運 | 同需求下比較遠倉／近倉或短長路線、兩人搶最後容量 | 是否看懂搬運耗時與瓶頸，有至少兩種可理解選擇；不靠無意義繞路／大量等待撐長遊玩 |
| G03 人口與維持 | 同條件少人／多人，展示貢獻與需求及一條缺貨恢復路徑 | 是否願意收人、能預備與恢復；先一種維持需求，不一併做食物／疾病／床位／全年生存 |
| G04 建造與保存 | 一個設施的藍圖／搬料／施工，或一種保存改善，二選一 | 是否看得出成本／進度／用途，取消與未完工不複製材料；腐敗不是建造原型的強制前置 |
| G05 補貨與自動化 | 在已驗證使用鏈上比較手工與一種改善，顯示釋放的時間及新代價 | 是否減少重複操作並保留有趣決策；不一次建電網／管網／物流網／符籙科技樹 |

圖稿／紙上研究不跑世界矩陣。未來若另批原型，才補與改動相應的同 tick 競爭、滿倉／空源／斷路、取消／重送、重複派單、暫停／存讀／倍率、施工與短缺恢復等必要反例；沿分層測試復用未變部分，不為每個候選先蓋完整測試框架。

## 放進目前規劃的位置

- #155 仍先建立第一個視覺／操作參照，D11 V1→V2→V3 與現有挑水小模型保持；本稿可供之後討論，不要求當前圖稿補廚房／臥房／電網或把模型擴成 Upkeep。
- D12 正式觀察／介入優先序保持。本稿可接「有意義的時間取捨」與後續村莊／安置問題；收錄不將新需求塞進 #154 原 DoD，不改 #140 原前置，不重排作者或預占下個工作包。
- 映射既有 BL-M01（距離／耗時）、S01（床位／設施名額）、S02／A01～A04（工作與自主）、S03（可達性）、S04／T01（配方／材料／設施）、#152 願景及村民安置；不開平行功能核心。#104／#105 可引用影響，不因此啟動戰鬥／整村自治。
- 開源原則沿 #145：先盤點現有 world／R2／預約與可復用 UI／素材；未來選一至兩個最接近候選的方案核對版本、license、適配與維護成本，必要才薄接線或自建。不因原稿提 Godot 就遷移，不在本次新增套件或編造開源效能結論。

待決策：生活經營與生存壓力的比重、現代設定／採購、第一種資源與使用者、節點或逐件倉儲、出發扣料與實體運送的相容、Upkeep／保存時間與短缺後果、玩家控制／分工、施工／取消、改善路線的代價。PO 建議先把「資源去哪了、改善後能多做什麼」展示清楚，再決定人口維持是否讓遊戲更好玩。
