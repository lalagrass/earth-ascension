## 1. 要解決的問題

玩家希望看懂：這個人天生擅長什麼、最近練成什麼、現在為什麼這樣做，以及變強後在地圖上有何實際差異。三版不必為了套一張卡先重寫規則。

**取欄位目錄的聯集；預設畫面精簡；同名異義保留分項；缺項不新增模擬。** 公版是資料投影與顯示契約，並非三版共用存檔或統一戰力公式。原量尺、點數預算、招式規則與作者成果保持。

## 2. 公版資訊架構

固定卡首＝頭像／姓名／身份／年齡階段（有資料才顯示）＋位置與當前行動；展開卡可加入半身／全身立繪，地圖小人物與施招動畫素材獨立引用。人物身份由各核心提供，不能因同名、同立繪或同座標認定同一人。

保留兩個主入口，詳細資料逐層展開：

| 區域 | 玩家看到什麼 | 展開內容 |
|---|---|---|
| 生活總覽：現在／原因／下一步 | 「正在挑水」「水缸不足」「交付後休息」 | 人工／自主來源、等待／缺料原因；只顯示核心提供的可用操作 |
| 生活總覽：身體與生活 | 精力與重要異常；有真規則才顯示生命、傷勢或其他需求 | 個別需求、恢復條件、短期效果；不另造一個生活總分 |
| 生活總覽：性情與相處 | 已知特質、志向、關係小事 | 價值觀與關係來源；MBTI／卦象／判詞放可選敘事欄，不直接等同能力或善惡 |
| 武學成長：稟賦與身體能力 | 根骨、悟性等資質；已有力量／身法／耐力等常態能力 | 能力可展開起始→目前常態→當下效果；來源未分明者標待核，不把創角值全叫先天 |
| 武學成長：練成的本領 | 腳力／力氣／生活技能／已學武學 | 當前值、歷史可核對的成長、實際效果、下一個有效學習方向 |
| 武學成長：實戰與演出 | 已有巡山／交手紀錄與招式說明 | 真傷害／距離／命中與返程；武學動畫設定另引用，不從動畫製造成果 |

桌面建議採暖紙色、低彩度水墨／水彩邊飾、清楚字體與留白。人物形象為視覺重點，數值仍要可讀；原始量尺放在值旁。這只是版面方向，沒有已交付的畫面稿／可操作 UI。

## 3. 聯集目錄與時間維度（R2修正）

**起點不是獨立能力類別，是每項能力／技能可有的開局快照。** 力氣、耐力與身法可同時有起始值及後續成長；並非放到起點就不能練，或放到後天就開局沒有。原稿 startingBaseline 改作可選來源／時間資訊，不建第二套會成長的數值。

| 類別 | 典型欄位 | 語義 |
|---|---|---|
| aptitude：稟賦 | 悟性、根骨、福緣、已知天賦 | 影響學習／潛力的原始規則；可有劇情覺醒，不宣稱永不變 |
| capability：身體能力 | 力道、身法、耐力；臂力／腿力／體魄為有真獨立作用才保留的細分 | 各有原版常態值及變更規則，是否可鍛鍊由核心證明 |
| skill／martial：技術 | 農事、採藥、烹飪、營造、輕功步法、拳掌腿／兵器套路與理解／熟練／體悟 | 會做／會打與有力氣分開；可開局已有技術，不等於先天天賦 |
| currentState：當下狀態 | 精力、生命、傷勢、飽足、心情、短期效果 | 與長期能力分開；耐力與精力剩餘不等價 |
| persona／relations | 特質、價值、志向、家人／師徒／好感與回憶 | 非戰力軸；保留已知程度與原有關係方向 |
| effectivePerformance／history | 當前走／跑速、負重、出招耗能、練功倍率、巡山紀錄 | 核心衍生結果或真事件；不另結算模擬 |

同一能力語義可附 initial（有來源的開局值）、base（目前常態，可能已含永久成長）、effective（本時點有效值）與真變動紀錄。三者不各自寫回核心、不默認線性相加，也不能從base反推initial。資源用current/max；**base不是出生值，current精力不是耐力**。

公版暫不把「腳力」當統一語義。舊字段標籤保留，請作者說是移速、長途運動本領、腿部出力或混合值。不要同一值映射身法／腿力／耐力再重複計分。腿法是踢掃等技術，輕功是移動武學，兩者都不自動等同跑得快。

最小方案建議先容納「力量／身法／耐力」，有獨立臂力／腿力效果的分支放細分；沒有耐力值則未支援，不為公版新增。是否要統一或採更多身體維度，待三方評估。詳見第二輪研究的取捨與掃堂腿紙上案例。

## 4. 最小資料投影約定（供評估，非可執行 schema）

卡片收一份唯讀快照：來源分支／固定 head、規則標識（沒有版本號則用 head）、角色穩定 ID、模擬時間、身份、行動說明與分組欄位。畫面不持有可改動的世界物件。

每項數值至少描述：

| 項目 | 用途 |
|---|---|
| semanticId／label／category | 不靠中文名稱或陣列順位猜對應；建議如 aptitude.comprehension、capability.agility、performance.moveSpeed、state.energy |
| availability | known、unknown、hidden、unsupported、ambiguous、notApplicable 分清；數值 0 必須仍是有效已知值 |
| rawValue／unit／domain／higherIsBetter | 保留原單位、上下限是否真界限、方向；不把原值全部乘成0–100 |
| provenance | sourcePath／branch／head、資料性質：權威值／已驗衍生／僅定義／fixture／未驗證；本包盤點不代表已跑通 |
| origin／changePolicy | 天生／創角基線／訓練／劇情／混合／未分；固定／可練／事件改變／未知 |
| initial／base／effective／modifiers；資源另用current/max | 起始快照／目前常態／當下有效值分清；僅已有來源才給，不反算／複製假基線，不把當前資源冒充能力 |
| visibility／comparisonGroup | 遵守角色已知資訊；是否可與另一數據比較及所用量尺版本 |
| growthEvidence（可選） | 有時間與真事件的前後變化；沒有歷史則只顯示目前值，不捏造原因 |

hidden 在投影輸出前遮罩，**不能只把真數字藏在 tooltip／DOM／事件解釋**。例：Grok 未揭露根骨／性格沿原規則，不因共用卡洩漏。未知、未實作與尚未相識也不是同一回事。

同一個語義若有兩份狀態（如 Gemini 既有工作 people 與新 persona），回報權威擁有人、同步方向與時點；尚未釐清用 ambiguous，不用 fallback 默默挑一份。

卡片操作只是意圖：按鈕→各版指令轉接→核心受理／拒絕與原因→新快照。研究稿只描述，不新增指令橋或 mutate core。

## 5. 雷達圖與武力值

聯集不等於一張十多角雷達圖。先用分組數值／條形；雷達作可選輔助，軸數由已定義且已知的同類資料決定。

- 「稟賦圖」與「練成的能力圖」分開；精力剩餘、性格、福緣不混成實戰六維。
- 不為湊六角新增技能，不把未支援的能力填0或隱藏天賦畫入輪廓。
- 比較兩人／前後，須同語義、同規則與同固定量尺；禁止每人自動放大。缺軸就不畫可誤解的封閉比較圖。
- 1–7、1–10、1–5 的端點對齊只表示各自範圍占比，**不是跨版能力等價**。要跨版同測，另定真正相同的情境、單位與條件，這輪不做。
- 當前速度以各版世界單位呈現；px/s 和 DU/s、不同地圖長度不能直接比較。武力總分保留各版來源，不訂公版戰力公式。
- Chart.js 的雷達可處理 labels／datasets／radial scale；本案若採用須明定固定 min/max，不能僅用 suggestedMin/Max 當硬邊界。簡單 SVG 也可，不為一張圖先引入大型框架。

## 6. 武學動畫放哪裡；不同人物要不要各做一套

建議拆成四份相互引用的資料，先評估，不新增 runtime：

| 資料 | 負責 | 不負責 |
|---|---|---|
| 武學規則定義／核心 | 招式合法性、姿態階段與權威時長、範圍、耗能、命中、位移、取消／受擊結果 | 美術素材載入 |
| 武學呈現模板 | 這招引用哪個 motionId、各階段如何演出、殘影／兵器軌跡／音效，命中與落空的不同表現 | 另一份出招耗時或傷害公式 |
| 人物視覺設定 | body／rig／spriteFamily、外觀／服裝、兵器握點／腳錨、可用動作、個人演法與必要 override | 修改人物能力／強制增速或送位移 |
| 素材目錄 | 圖格／圖集／骨骼、方向、錨點、來源與授權、版本 | 保存角色戰鬥狀態 |

**不是「人物數 × 招式數」全部重做。** 同體型／相容骨架共用基礎起手／出掌／收勢，外觀換 skin／attachments；武學選動作，人物可另選剛猛、輕巧、生澀等視覺變體。不同武器或比例差異大時需要對應的動作族；招牌招式／重要人物才做專用演出。

但水彩逐格 sprite 不能靠換頭像自動得到完整動作，通常仍需對應人物圖格；骨骼換裝能重用動作，也需處理關節比例、遮擋與握點，不能保證任意身形無縫套用。先清點現有素材，不先決定買 Spine／換 Godot／重做全員骨架。

解析優先序建議：合法的角色專用變體→相容身形／兵器動作→通用相容動作→中性簡化姿態。缺圖不妨礙核心結算；不可把持劍硬套空手素材而誤導玩家。每項 fallback 在評估報告列明。

動畫讀實際 action ID、施展者、招式、phase、phase progress、朝向／目標位置及 hit／miss／cancel 結果。攻擊開始、命中／落空與取消要可區分，核心事件 ID 防重播特效；低幀率／暫停不重扣精力、不補造傷害。模型權威位移由核心提供，視覺動作不得另跑 root motion 改座標。快慢由真實招式階段／移動速度映射，不因套不同人物素材偷偷改攻速。

「初學搖晃、高手俐落」若只是既有時長內的演法可作視覺選項；若要改命中、招式耗能／時長或解鎖條件，是後續玩法決策。

## 7. 可參考的社群／開源

核對日期 2026-10-26；以下是可借用的組織方式，沒有安裝或驗證直接套入：

| 參考 | 借用之處 | 邊界 |
|---|---|---|
| [Fari 人物卡框架說明](https://keeper.farirpgs.com/resources/fari-rpgs/fari-app-wiki/managing-characters/) | 頁籤→區塊→文字／數值／技能／計數器，精簡卡可選顯示區塊；最符合欄位可擴充方向 | 本輪依官方文件研究設計，未核實 Fari 程式版本／授權或選為依賴 |
| [Roll20 社群人物卡](https://github.com/Roll20/roll20-character-sheets) | 大量 HTML/CSS 表單與分頁排版；repo 說明人物卡程式以 MIT 發布 | Roll20 的欄位／sheet worker 依賴須轉接；遊戲規則與圖片另外核來源，不能整包當通用網頁庫 |
| [Foundry dnd5e](https://github.com/foundryvtt/dnd5e) | Actor 資料與人物 sheet，能力、物品、特性分工 | 軟體 MIT、規則 SRD 與圖像另有條款，且依賴 Foundry 平台；不是零成本可嵌入元件 |

## 8. 三方回覆後的落地順序與驗收

1. 三位 agent 各交一份唯讀評估，回主 issue 同一表；有正在開發的包就在穩定交付點再評估，不強制停工／搬分支。
2. PO 集中確認欄位語義、資料主權與哪些是真後天成長，尤其 Gemini 雙狀態和別名、Grok 根骨／悟性與創角／skills 的關係、GPT 基礎值是否有獨立成長來源。
3. 另行選定一個可見工程包：一張公版卡＋三份轉接；再決定要不要加動作模板。不能把本文件接受當成工程授權。
4. 之後工程先用既有靜態人物資料與缺項／隱藏／雙來源／同名異義範例驗欄位，再接每版一個真實流程；只驗直接變動，不為卡片重跑整套世界矩陣或手機。研究階段不用啟服務／開測試分頁。
5. 本包完成條件＝設計、固定快照對照、三份 prompt、開源與限制、未定事項齊全；三方尚未回覆與未接線明記；R2新增經典／腿法研究與提示詞問題，只擴充評估、不授工程。不以此重開存檔升版或第二試玩入口。

待定：三版是否接受分類、起點與真先天如何分、哪些可當共同語義、第一張卡先放哪些值、雷達是否值得做、動畫先用現有逐格／程序姿態或另案骨架、誰主筆工程及其正式授權。沒有預設三版必須新增同一組屬性。
