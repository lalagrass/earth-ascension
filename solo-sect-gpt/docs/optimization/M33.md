# M33 同一人物的工作目標與自主控制：實作前規格

base `526dd1a`（M32 交付）；規劃 GPT / Codex（M31-M36-PLAN），實作主筆 Claude Opus 5.5（Anthropic），單一作者。本節先 commit，結果另列。

## 玩家問題與來源

人物頁的「停工／恢復自主／開關自主」一排按鈕和情境卡裡的同類按鈕重複，卻看不出「原本要做什麼、這趟臨時工作做完回哪裡、為什麼在休養、是誰卡住他」。

- 新公版 6f959f5：`intent-view/contract.mjs`（`intentView`、`validateRequest`：送出前核人物、指令 id、payload 是否還是當下那一份）、`intent-view/render.mjs`（`intentHtml`／`commandHtml`）、`public-fix/view-state.mjs`。`intent-view/gpt.mjs` import 舊核心——不採用。
- 本核心權威：`p.intent`（玩家已受理的工作）、`p.temporary`（臨時一次：種類、世代、做完要回的 intent／auto／停工）、`w.pendingCommands` 中屬於本人的排程命令（`executeTick`）、`p.manualStop`、`p.auto`、`p.recovering`、`commitmentOf`（遠征、演練、同堂等 owner）、`situation`／`describeLife` 的現在／原因／下一步、`goalSource`（M21）、既有命令 `stop`／`resume`／`auto`／`recall`／`task`。

## 修改範圍

1. 採用 6f959f5 的 `intent-view/{contract,render}.mjs`（只改 import），`SOURCES.md` 補列。
2. 新增 `src/intent-view.mjs`：`createGptIntentAdapter({getWorld})`。`snapshot(id)` 分欄：現在活動與原因（取自 `situation`）、目標來源（M21 `goalSource`，查不到就 unsupported——不挪用當下原因）、玩家指令 `intent`、臨時工作（做完回哪裡）、本人的 `pendingCommands`、明確停工、自主開關、必要休養、目前 owner（取自 `commitmentOf`）、主次職務。自主政策只有開關，政策原因本核心沒有公開查詢 → unsupported。命令清單：坐休、回床睡、吃飯、取用乾糧、停工、恢復自主、開／關自主、叫回，各有穩定 id 與快照 payload，啟用與否用核心預判（`predict`）。`validate(request,expectedActor)` 用公版 `validateRequest` 重取當下快照比對，通過才回傳要送的命令。
3. 介面：人物頁生活總覽用 `intentHtml` 取代原本那排「坐休／回床睡／吃飯／取用乾糧／停工／恢復自主／開關自主／叫回」；情境卡裡為受阻或共享安排給的操作（叫停交手、全隊召回等）保留。點擊 intent 按鈕時先 `validate`，再經既有 `send` 送出一次（臨時一次的勾選照舊套用），然後 return，不會再落到舊的 handler。每人最近一次回覆存在本頁、只顯示在該人卡上；成功換世界清空，讀檔失敗保留。
4. 不新增排程、佇列或 AI；遠征召回、演練退出、共享活動的限制都沿核心 owner gate。

## 事前驗收

1. 投影不改世界；有讀與沒讀 intent 面板的同命令 twin 結果與 RNG 相同。
2. 分欄正確：給工作→intent 有值；臨時一次採木→temporary 寫回原安排；`executeTick` 排程命令出現在 pending、執行後消失；停工→manualStop true；關自主→auto false；傷勢 70（標註 fixture）→必要休養；同堂中→owner 是同堂；小禾的練功被拒；成熟訪客（matureGuest 局的宗師）只能接自理類命令。
3. 過期與重複：A 的快照按鈕拿去對 B 送→「人物已切換」；狀態改變後舊 payload→拒絕；同一請求連按兩次，第二次按核心目前狀態重驗、只會各自送一次（命令紀錄計數）。
4. 正常 UI（1440×900、1280×800）：原工作（採木）→ 勾臨時一次改去採菜 → 做完回原採木；受傷者必要休養後續作（沿 M25 存檔）；明確停工 → 恢復自主；至少兩名角色之間切換，舊按鈕不套到新人物；每人的最近回覆只在自己卡上。
5. 回歸全過。

## 實作紀錄

- `vendor/public/6f959f5/intent-view/{contract,render}.mjs` 原樣採用（只加來源註解），`SOURCES.md` 補列；同目錄 `gpt.mjs` 綁舊核心，不採用。`public-fix/view-state.mjs` 本階段沒有用到，未採入（M35 處理展開與焦點時再決定）。
- `src/intent-view.mjs`：`createGptIntentAdapter({getWorld})`。工作目標讀 `p.intent`；臨時工作讀 `p.temporary`（做完回原指令／回原停工／回自主日課）；待改派列本人的 `pendingCommands` 與執行 tick；明確停工讀 `manualStop`；恢復欄分「必要休養（保留原指令）」（核心 `recovering`）與「必要自理」（自主日課以 `必要自理` 原因選的休息／睡／吃），其他寫「沒有」；叫回讀 `intent.kind==='return'`；共享安排讀 `commitmentOf`，沒有就不適用；目標來源讀 M21 `goalSource`，查不到寫不支援；自主政策原因本核心沒有公開查詢 → 不支援。八個按鈕的啟用與原因都用核心預判。
- `person-view.mjs` `predict`：補上個別「叫回」的預判（與核心送出前的同一個檢查）。修前倒地者的「叫回」顯示可按、核心卻拒絕（「倒地者需要救援」），由下面第 2 項的逐鈕比對找出。
- `ui.mjs`：人物頁生活總覽用 `intentHtml` 取代原本那排八個按鈕，下面一行補臨時工作、自主、共享安排、目標來源。按鈕保留舊的 `data-task`／`data-action` 名稱讓既有驅動與快捷照用，但點擊只走 intent 路徑：先 `validate`（核人物、指令 id、payload），通過才經 `send` 送一次（臨時一次的勾選照舊），然後 return。每人「最近一次操作」只記在本頁、只顯示在該人卡上；換世界（成功讀檔、新局）清空，讀檔失敗世界不變所以保留。情境卡裡叫停交手、全隊召回等 owner 操作不動。

失敗紀錄：第一次 UI 驅動在切人步驟失敗，是驅動假設林青沒有回覆（其實 `calm` 剛按過他的停工），改斷言為「阿木的回覆沒有出現在林青卡上」；第二次在受傷步驟逾時（`m33-ui-failed-selfcare-1440`）：沈禾是自主日課選的必要自理，不是核心 `recovering`，面板「恢復」欄原本只看 `recovering` 而寫「否」。改成分開寫兩種休養後重跑通過。

與規格不同：受傷者的正常 UI 路線是「必要自理→回日課」，不是「必要休養→續原指令」——傷勢超過 60 時核心拒收新指令，正常畫面做不出帶原指令的必要休養；這條由模型（標註 fixture）驗。成熟宗師的停工／自主開關／叫回核心照收，所以面板照實可按。

限制：布林值以原值字樣呈現（例如「明確停工：true」），M35 統一值呈現時處理。

舊驅動重跑（1440×900）：M25 驅動（用舊的 `data-task="rest"`／`data-action` 名稱點新面板）通過，`m25-ui-m33-recheck-1440`。M30 路線驅動在第 2 步失敗（`m30-route-ui-m33-recheck-1440`）：它斷言林青背包一有菜就「正在送來」，這正是 M31 修掉的口徑（還在野外採集、未進送回階段不算在途）；與 M33 無關，M36 的新路線改寫此步。
