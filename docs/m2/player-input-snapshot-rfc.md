# 玩家輸入與不可變快照 RFC

狀態：2026-10-17 設計提案，對應 [M2 #11](https://github.com/lalagrass/earth-ascension/issues/11) 的**文件階段**；尚未實作或驗收。此 RFC 也為 [M3 開放方向](../m3/creator-briefs.md)與 [D4 #22](https://github.com/lalagrass/earth-ascension/issues/22)提供輸入時間契約，但不批准 M3 程式。版本與 RNG 的前置見 [#10](https://github.com/lalagrass/earth-ascension/issues/10)。

## 問題與現況證據

目前 `Store.create_character()` 與 `Store.set_legacy_goal()` 在 `BEGIN IMMEDIATE` 內讀取當月快照，直接更新 `snapshots.state`，再以 `INSERT OR REPLACE` 覆蓋同月 `state_hash`（見 [`store.py`](../../earth_ascension/store.py)）。前端在提交後立即 `load()`，因此新人物／新目標立刻出現在「現況」。`GET /api/world?month=N` 也從同一筆已被改寫的快照讀取，無法指出第 N 月的月度結算狀態與其後玩家提交的差別。這與 [M2 技術方案](technical-design.md#隨機數版本與回放)的歷史快照不可原地重算、[A9 回放](acceptance.md#可執行案例與通過線)及 M3 推進前輸入需求衝突。M1 也有當月即時改寫行為；本 RFC **不改 M1 legacy 路徑**。

以下是**設計選擇**，不是已存在的 API／資料表。沒有以前的輸入日誌時，不能從現有最終快照推斷舊修訂順序或補造事件。

## 必須維持的不變量

1. `S_m` 是第 `m` 月已提交的世界快照；一旦產生，其 JSON 位元內容與 `H_m = canonical_hash(S_m)` 永不因後來的玩家輸入而改寫。歷史查詢只讀 `S_m`。已提交的事件來源、月份與人物當時可知資訊不回填。
2. 玩家在 `S_m` 之後、下一次推進截止前提交的輸入是獨立的追加式命令，不是 `S_m` 的一部分。現況頁可顯示**待生效預覽**，但須與已提交世界狀態分欄；歷史月不得顯示預覽。
3. `advance(expected_month=m)` 在同一交易中確定本月截止的命令順序，從 `S_m` 建立第 `m+1` 月的共同決策快照；輸入對第 `m+1` 月生效。所有 NPC 只看到該決策快照中合理可知的資訊。其後結算與 `S_{m+1}` 一次提交，失敗全數回滾。
4. 相同起點、規則／資料／RNG 版本、seed 及**同一份有序命令日誌**必須產生相同 `S_{m+1}` 與 hash。重送不得二次建人或二次重選；審計用牆上時鐘與網路請求 ID 不得進入 canonical 世界狀態。
5. M1 舊存檔的建人、目標與推進語義照原版運作。M2 0.2.0 舊檔不能被無聲改標成新契約；採複本遷移並保留來源，或明確拒絕跨版本寫入。未知／損壞版本安全拒絕。

## 方案比較與推薦

| 方案 | 玩家提交後所見 | 好處 | 代價與拒絕條件 |
|---|---|---|---|
| A：追加式待生效輸入（**推薦**） | 已提交世界仍為 `S_m`；另顯示待生效人物／目標與預計生效月 `m+1`。推進後取得正式人物 ID 與事件。 | `S_m`／`H_m` 真正不變；同一時間邊界可沿用於 M3 開放方向；命令日誌可檢查重送、撤回與因果。 | 現有 M2 `POST /api/characters` 的「立即回傳正式人物並可在歷史月看到」語義要明示改版；UI 必須展示 pending 與失敗原因。若不能一起提供可用預覽，不應只改儲存層。 |
| B：追加式修訂鏈 | 保留 `S_m`，每次提交另存 `R_{m,1…n}` 與 hash；現況指向最新修訂，歷史查詢顯示原版或選擇修訂。 | 現有即時建人感受較接近；每次變更仍可追溯。 | 要同時定義「第 m 月」究竟指 `S_m` 還是 `R_{m,n}`，多版本讀取、同月事件可見性、修訂順序、重送與 hash 選擇都較複雜；若仍覆寫 `S_m` 或只保留最後 hash，直接不合格。 |
| C：維持覆寫、只改文字說明 | 立即看到結果。 | 實作量最小。 | 無法證明原 hash、輸入順序或歷史當時狀態，不符合本 RFC 的 A9 與回放不變量；不採用。 |

推薦 A 是因為玩家原本就說「**推進前**給方向」，輸入可以是下一次決策的條件，而非重寫已發生的月份。此判斷以產品語義和目前存檔行為為依據；正式實作前仍要用下列 fixture 檢查 UI 代價與舊檔處理，若無法滿足則回到 B 重新審核，不能偷用 C。

## 方案 A 的最小契約

- **命令。** 待生效紀錄至少有 `command_id`、`expected_month`、`effective_month=m+1`、輸入類型、已驗證 payload、提交順序、狀態與原命令引用（修訂／撤回時）。伺服器在交易中指派穩定順序；客戶端 idempotency key 只用於去重。紀錄提交時間可供操作審計，但不參與模擬或 canonical hash。原文輸入須保留，不能由文字猜測世界事實。
- **提交與回應。** M2 建人／目標重選提交後回傳收據與 pending 預覽，而非宣稱已改 `world`；UI 明示「第 `m+1` 月生效」。M1 保留現有同步回應。若新端點或回應格式與 M2 現有客戶端不相容，須明示版本及前端同步改造；不可讓舊前端把 pending 當已成立人物。建人的正式 person ID 在推進交易中依確定順序配發；預覽使用 `command_id`，不提前占用 `world.next_id`。
- **驗證與截止。** 提交時檢查身分、玩家可控制人物、存活、點數、目標類型、最多三名玩家人物（含尚未生效且未撤回的建人）、`expected_month` 與欄位長度；推進時對凍結的輸入集合重驗。推進交易開始後到達的請求要等待並以新月份重新驗證；帶舊 `expected_month` 者拒絕，請玩家重新載入，不靜默套到下一月。
- **修訂／撤回。** 對尚未生效的同一命令只能追加新命令引用前項；原紀錄不刪不改。截止時依明示順序求有效輸入，撤回者不進決策；已生效者不能追改歷史。對已生效的 M3 方向若允許撤回，應是下一月的新方向狀態事件，不抹除原採納與工作證據。
- **結算與來源。** 在 `advance` 中套用有效命令並生成第 `m+1` 月帶 `command_id` 來源的建人／目標事件，再形成共同決策快照。命令順序、採納／拒絕結果及來源進入可回放紀錄；`S_{m+1}` 的 canonical hash 只由確定性資料計算。不存在的事件或未知情報不得因輸入文字變成角色知識。
- **讀取。** `GET /api/world?month=m` 永遠回已提交 `S_m`；live 讀取另帶待生效收據與預覽，不混入 `world.people`、`world.events` 或 `state_hash:m`。歷史 UI 可在第 `m+1` 月追查輸入結果，但不把第 `m+1` 月的人物／目標投影回第 `m` 月。

## 舊檔與版本邊界

M2 0.2.0 只保存目前可見的快照與 hash，部分月份可能已被玩家覆寫。**不能**補造缺失的原 `S_m` 或宣稱舊 hash 從未變動。後續遷移 PR 應以一致性 SQLite backup 複製到新路徑，記錄來源版本／截止月份及能涵蓋待寫 WAL 的來源指紋（見 [#6](https://github.com/lalagrass/earth-ascension/issues/6)），驗證舊歷史依其**實際保存內容**可讀；以最後一個現存快照作新的明示邊界，標記此前輸入來源未知。若尚無可驗證的 M2→新契約遷移，舊檔可唯讀查閱，跨契約續玩須明確拒絕；原版本程式／commit 須留存供來源續玩。不要在這份 RFC 直接擴充 `COMPATIBLE`，也不要把未實作的遷移說成現有功能。

需要規劃一組相互獨立的小 PR：先鎖資料／API／UI 生效語義及舊檔 fixture，再做追加式命令與原子消耗，再同步調整 M2 前端及遷移；每份 PR 都保留 M1 路徑，最後用完整回放與瀏覽器驗收。當中若有階段無法讓現行 UI 正確顯示 pending，就保持 draft，不先合入半套新語義。

## 可執行驗收與失敗條件

1. **不覆寫。** 在第 0、12 月各保存 `snapshots.state` 與 `state_hash:m`；建人、目標重選、修訂、撤回後兩者逐位元不變。歷史查詢不見 pending，live 明示 pending；推進到 `m+1` 後才有正式人物／目標與來源事件。
2. **重送與競爭。** 同一 idempotency key 重送 2 次只有一筆有效命令；不同客戶端同時提交有穩定順序；三人上限含 pending；在推進截止後提交舊 `expected_month` 明確拒絕。建立人物與目標重選同月提交，套用順序和身分檢查可重現。
3. **原子與因果。** 在寫命令、套用命令、寫 `S_{m+1}` 前注入故障，重啟後要嘛仍待處理、要嘛完整提交一次，不能出現人物、事件、hash 半套。第 `m+1` 月決策只用截止時已確認的輸入與月初共同快照；來源 event ID、月份及身分均可追溯。
4. **回放與舊檔。** 同一 seed、版本與有序命令日誌兩次運行得到完全相同逐月 hash；原 0.2.0 無輸入路徑的既有 golden 測試不意外改變，新規則版另鎖自己的基線。M1 0／12／60 月建人、推進、重啟及歷史回歸；M2 0.2.0 來源檔位元不變，明確遷移或拒絕，未知版本拒絕。
5. **瀏覽器。** 真實瀏覽器檢查 M2 待生效人物／目標、推進後正式 ID、歷史月無回填、重送／失敗訊息與 M1 六頁；M3 將來新增方向輸入時沿用同一時間與預覽契約。

任一已提交 `S_m`／`H_m` 被覆寫、pending 在歷史月偽裝成已發生、同一請求重送產生兩次人物、輸入不經交易截止而影響後遍歷 NPC，或為通過測試補造舊命令，皆為阻擋。此 RFC 合併僅決定後續實作的設計起點；[#11](https://github.com/lalagrass/earth-ascension/issues/11) 要等程式、遷移與驗收 PR 完成才可關閉。
