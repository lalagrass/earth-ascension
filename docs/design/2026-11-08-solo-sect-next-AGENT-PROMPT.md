## 一、合作方式

1. **每做完一個 PR，就重讀 #488**，從最上面還沒打勾的一項接著做。Claude 在 #488 新增或調整的項目都算範圍內，直接做，不用問擁有人。

3. **有疑問時**，在當下的 PR 或 #488 留言給 Claude，然後先照最合理的讀法繼續做，並寫進 PR 的「最沒把握的三處」。只有「五」列的情況才停下來。
4. **開工前**，在該項的 issue（或該輪索引 issue）留一則認領，列出要做的 milestone。
5. **review 意見回來時**，修在被 review 的分支上，再 merge 進你手上的分支。不要 rebase 已推上去的分支，也不要 force push。修完在那個 PR 留言說明，再回到手上的工作。

## 二、每個 PR 怎麼做

1. **規格在 issue 裡。** 讀索引 issue 和每個 milestone issue 的全文，照內文做。
2. **一個 milestone 一個 commit**，訊息開頭寫編號，例如 `feat(solo-sect): R4 ...`。
3. **分支與 PR**：從上一個 PR 的分支開新分支（上一個已合併就從 `codex/solo-sect-grok` 開）。PR base 一律設 `codex/solo-sect-grok`，描述第一行寫疊在哪個 PR 上。
4. **改到模擬的 PR**：用 Node 22 重產 golden，PR 寫明哪些 golden 為什麼變。擁有人 2026-11-08：存檔等遊戲能玩後再做，**現在不保證存檔相容**，不用加 `MIGRATIONS`。`RULES_VERSION` 仍要升一版，讓載入時能認出不同版的存檔並拒絕。只改畫面、文件或測試結構的 PR，golden 不變、不升版。舊開局已淘汰（R9），只有 `hermitage` golden。
5. **同步文件**：ROADMAP、FEATURES、DECISIONS、該系統的文件（例如 `hermitage.md`）；`NEXT-MILESTONES.md` 每步寫三行：借了什麼、沒借什麼、為什麼。`solo-sect/REVIEW.md` 加本 PR 一節。
6. **測試從輕**：本地每步只跑 `bash solo-sect/test/run.sh smoke`；每個 milestone 最多新增一個小測試；完整測試交給 CI。
