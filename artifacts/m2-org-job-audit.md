## 第一部分：M1→M2「組織進展」事件遺漏唯讀核對與回放影響量化

### 1.1 程式碼逐行核對（`engine.py` vs `m2.py`）

對照 M1 [`earth_ascension/engine.py:196-203`](../earth_ascension/engine.py) 與 M2 [`earth_ascension/m2.py:540-545`](../earth_ascension/m2.py)：

| 欄位／邏輯 | M1（`engine.py:196-203`，`0.1.0`） | M2（`m2.py:540-545`，`0.2.0`–`0.2.2`） | 核對結論 |
|---|---|---|---|
| 活躍成員篩選 | `researchers = [world["people"][str(i)] for i in org["members"] if world["people"][str(i)]["alive"]]` | 完全相同 | 一致 |
| 單月研究進展計算 | `progress = sum(p["skills"]["研究"] for p in researchers) // 30` | 完全相同 | 一致 |
| 組織狀態更新 | 更新 `org["research"]`、`org["resources"]`、`org["activity"]` | 完全相同 | 一致 |
| `progress >= 3` 事件 | `if progress >= 3: _event(world, "組織", None, f"{org['name']} 研究進展 {progress}", [f"活躍會員 {len(researchers)}", "會員研究技能累計"])` | **缺漏（未呼叫 `_event`）** | **M1→M2 移植遺漏** |

- **原因分析**：M2 完整保留了 `org["research"] += progress` 與 `org["activity"] = f"會員累計研究進展 +{progress}，維持服務"`，但漏掉最後兩行 `if progress >= 3: _event(...)`，導致 M2 世界中五個組織雖然每月照常累積研究進展，卻從未在 `world["events"]` 留下任何 `"組織"` 事件。

### 1.3 第一部分結論與版本建議〔提案〕

1. **絕對不可直接修改 `0.2.0` / `0.2.1` / `0.2.2` 現有規則分支**：因為 `m2:{month}:{len(world["events"])}` 使用全域陣列長度編碼，補回 `"組織"` 事件會使所有 seed 從第 7–12 月起改變 **86.2%** 的 `event_id` 與 `canonical_hash`，直接破壞 `test_golden.py` 與既有存檔的因果 ID 對照。
2. **若於未來新 `rules_version`（如 `0.2.3+`）補回組織事件，建議由「每月重複洗版」改為「里程碑式觸發」〔待決策〕**：
   - 在 M1 原條件 `progress >= 3` 下，第 12 月後幾乎每個組織每月都觸發（60 月共 ~200 筆），會稀釋「世界編年史」的可讀性。
   - 建議在未來新 `rules_version` 中，僅於組織 `org["research"]` 跨越里程碑門檻（例如每跨越 `25 / 50 / 100` 點，或首次達 `progress >= 3`）時產生一筆 `kind="組織"` 事件，並嚴格以 `world["rules_version"]` 隔離，保留 `0.1.0`–`0.2.2` 原有回放。

## 第二部分：玩家 60 月路徑的最小身分／職業轉變與組織歸屬規格

### 2.1 現況問題與為什麼不能「只依最高技能授職」

1. **現況（`0.2.2`）**：[`store.py:83`](../earth_ascension/store.py) 創建玩家人物時固定寫入 `age=20, job="學生"`，且未加入任何 `world["organizations"][oid]["members"]`。推進 60 個月（25 歲）後，即使玩家人物已完成多次階段目標、技能達 30–45，畫面仍顯示 `25 歲 · 學生`，組織名冊也永遠沒有玩家人物。
2. **反例證明（為何不能只看最高技能自動轉職）**：
   - 以 `artifacts/run_m2_org_job_audit.py` 中的對照人物 **「張緩步」**（`unqualified_student`：初始目標「探索靈氣」，但 `悟性=3, 感知=3, 意志=8, 盡責=1.0`）為例：
   - 在 `seed 2026` 推進 60 個月後，張緩步因研究計畫停滯（觸發 `目標受挫`），計畫行動被改為「工作」（[`m2.py:371`](../earth_ascension/m2.py)），60 月累積 `工作=45, 研究=5, 社交=7`，但**整整 60 個月從未完成過任何一次「探索靈氣」階段目標（`goal_history = []`）**。
   - 若規則只看「某項技能 ≥ 門檻」就自動授職，張緩步會在目標受挫、從未完成人生目標的情況下被憑空授予「工程師／商務」頭銜並塞入產業協會，違背玩家設定的「探索靈氣」生命敘事與因果可追溯性。

### 2.2 最小可追溯規格提案（Event-Sourced Identity & Organization Transition）〔提案〕

為確保每一筆職業變更與組織入會都有**明確事件來源、雙向名冊一致性與不達標對照**，最小規格分為兩個層次：

#### 層次 A：純 UI 語義澄清（零規則變更，可隨時套用）
- 若在未升級 `rules_version` 前僅調整前端顯示，Dashboard 不得暗示玩家已就業或轉職，應將玩家創建時的 `"學生"` 明確標示為 **`學生（初始身分）`**（或在創角頁註明「初始身分：學生」），避免與經歷事件後的職涯狀態混淆。

#### 層次 B：下一版 `rules_version`（如 `0.2.3+`）最小職涯／入會規則（待校準）

1. **觸發時機與前置條件（四項必須同時滿足）**：
   - **檢查時點**：月末結算 `_progress()` 完成後，僅對 `person["alive"] == True`、`person["job"] == "學生"` 且 `person["months_lived"] >= 12`（至少生活滿 1 年、年滿 21 歲）的人物檢查一次。
   - **事件前置（Causal Milestone）**：`person["goal_history"]` 中必須存在至少一筆 `stop_reason == "target_reached"` 的已完成目標 `G`，且個人編年史 `person["chronicle"]` 中存在對應的 `kind == "目標完成"` 事件 `E_complete`（`E_complete["effects"]["goal_id"] == G["id"]`）。
   - **領域技能門檻（待校準，基準值 `12`）**：已完成目標 `G["type"]` 對應的領域技能須達標，映射如下表：

| 已完成目標 `G["type"]` | 領域技能條件（待校準） | 轉變後職業 `person["job"]` | 歸屬組織 `org_id`（`org["name"]`） | 必要因果事件來源 `causal_event_ids` |
|---|---|---|---|---|
| `探索靈氣` | `skills["研究"] >= 12` | `研究員` | `1`（`市立新現象研究所`） | `[E_complete["event_id"]]`（若本人已有 `practice_basis`，併列其 `source_event_id`） |
| `累積財富` | `skills["工作"] >= 12` | 工業灣為 `工程師`；其餘區域為 `商務` | `3`（`灣區產業協會`） | `[E_complete["event_id"]]` |
| `服務社群` | `skills["社交"] + skills["工作"] >= 12` | 河港為 `醫護`；學園為 `教師`；其餘為 `服務業` | 河港 `2`（`河港醫療聯盟`）／學園 `5`（`學園教育網`）／其餘 `4`（`舊城互助會`） | `[E_complete["event_id"]]` |
| `建立關係` | `skills["社交"] >= 12` | `行政` | 學園 `5`（`學園教育網`）／其餘 `4`（`舊城互助會`） | `[E_complete["event_id"]]` |

2. **事件紀錄與因果鏈（Event Source）**：
   - 達標當月由引擎產生一筆 `important=True` 的可追溯事件：
     - `kind`: `"職涯"`
     - `actor` / `subject`: `person["id"]`
     - `text`: `f"{person['name']} 完成階段歷練，轉任{new_job}並加入{org['name']}"`
     - `causes`: `[E_complete["event_id"], ...]`（使 `causal_event_ids` 精確指向觸發該次轉職的 `"目標完成"` 與 `"發現"` 事件 ID）
     - `effects`: `{"job_before": "學生", "job_after": new_job, "org_id": org["id"], "goal_id": G["id"]}`
3. **名冊一致性不變量（Roster Consistency Invariants）**：
   - 轉變時將 `person["id"]` 加入 `world["organizations"][str(org_id)]["members"]`（若尚未在列），並維持 `members` 依 `pid` 升冪唯一（`len(members) == len(set(members))`）。
   - `validate(world)` 驗證：任何被 `"職涯"` 事件寫入 `effects["org_id"] = k` 的人物，`person["id"]` 必須存在於 `world["organizations"][str(k)]["members"]`，且同一人物至多屬於一個組織。
   - 一旦加入組織，次月起該玩家人物的 `skills["研究"]` 自然納入 `m2.py:541` 的 `researchers` 計算，使玩家角色的研究成長真正貢獻於所屬組織的 `org["research"]`。
4. **Dashboard 呈現方式**：
   - **人物觀察（`observer`）**：副標題顯示所屬組織徽章（如 `22 歲 · 研究員 · 市立新現象研究所 · 學園 · 在世`；未轉職前顯示 `20 歲 · 學生（初始身分） · 尚無所屬組織`）。
   - **組織分頁（`organizations`）**：成員名單中對 `p.player === true` 的成員加上 `✦ 玩家` 標記，點擊可直接跳轉至該玩家人物觀察頁。
   - **生命歷程（`chronicle`）**：`"職涯"` 事件因 `important=True` 與具備 `causal_event_ids`，可直接在時間軸呈現並點擊跳轉至觸發轉職的 `"目標完成"` 歷史月快照。
